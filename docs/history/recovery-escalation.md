## Takeover inspection

`ctask takeover-status WORKFLOW --request ID` reads the existing recovery ledger without changing it. It returns `eligible`, `reasons`, request details, current generation and status, STOP, owner and deadline facts, and a safe next action. The same checks run again during `takeover` under the recovery lock. Reasons distinguish `stopped`, `unknown_request`, `replaced_request`, `generation_changed`, `status_changed`, `expired`, `supervision_window_expired`, `disabled`, `binding_changed`, `contract_changed`, `already_handled`, `owner_active`, `repository_busy` and `repository_unavailable`. Eligibility is a snapshot, not a reservation. Neither inspection nor rejection extends any deadline, clears STOP, or creates a recovery request.

## Quiet operational ownership

In `user_input_only` mode, an idle blocked/error workflow can acquire a durable `operational` follow-up for its episode. This is diagnostic-only, never a business repair or grant. Before any at-most-once origin message the controller checks the current workflow, STOP, owner, repository lock, recovery binding and existing delivery/handler, successor link, existing questions, and origin-turn evidence. An active or ambiguous origin, ambiguous or outstanding recovery delivery, invalid lineage or question, and an unavailable adapter stay visible without a wakeup. An origin equal to the hub is recorded locally and never self-queued. The durable outbox preserves dispatching/unknown outcomes across restarts; no fresh identifier is used to replay an uncertain send. A response alone does not prove recovery. Actual STOP prevents operational follow-up; a verified successor or independently observed execution progress can close the generic follow-up, without altering predecessor state. The policy does not change Drover mute or quiet hub notifications.

When a verified bound origin or hub has established a real user need, `ctask operational-disposition ID --category decision --blocker 'specific question' --tried 'specific steps' --evidence /absolute/immutable/file --recommendation 'specific recommendation' --source 'actual diagnosis source'` records a canonical pending question. Other permitted categories are `handler_assignment`, `permission`, `missing_information`, and `manual_acceptance`. Multiple `--evidence` options are supported. Evidence is SHA-256 pinned and rechecked; the context contains task, blocker, tried steps, evidence and recommendation. It uses the existing canonical `question-…` format and normal answer/accept path with explicit controller provenance, without inventing an answer, acceptance, or expanded authority. One question per episode is supported; conflicting replacement is rejected. Technical timeout alone is not a user decision.

## Independent lineage

`ctask workflow-link PREDECESSOR --successor SUCCESSOR --evidence /absolute/lineage.json --source 'actual verification source'` records metadata only, from the verified origin or current hub. It requires the same actual Git repository, bound origin and hub, unmodified contract hashes, unchanged authority, grants and limits, preserved original scope, a complete one-to-one mapping retaining each original criterion including commands/manual gates, and a completed successor with passed evidence. It rejects cycles and conflicting relinks. STOP is an execution fence and is not removed. Repeated identical registration is idempotent.

The JSON evidence contains absolute `predecessor_workflow` and `successor_workflow`, raw-file SHA-256 values `predecessor_contract_sha256` and `successor_contract_sha256`, `permission_expanded: false`, `origin_thread`, `hub_thread`, an `acceptance_mapping` object mapping every predecessor criterion ID to the matching successor criterion ID, and a nonempty `source` or `note`. If the successor appends a scope annotation, the original scope must remain an exact prefix; `scope_annotation` must equal the appended text and `scope_annotation_observation_only` must be true. This is an attestation by the bound origin or hub, not automatic proof that natural-language text cannot be read as authority; the link itself grants no execution authority. The metadata pins the evidence file, raw and semantic contracts, origin files, completed successor state, and each criterion evidence file. It never executes evidence. `status PREDECESSOR` preserves raw status and history and adds `delivery.raw_status`, `effective_status`, successor and verification details. Tampering or unavailable evidence is visible as invalid and does not assert completion. The controller reconciles generic followups as metadata only.

The historical Archify lineage file lacks a successor contract hash and mapping. An operator would need a separate enriched evidence wrapper containing the original lineage file's path and SHA-256, both actual contract hashes, explicit criterion mapping, the exact appended scope annotation with its observation-only attestation, and verified origin/hub bindings; it must not rewrite the historical file. This candidate does not create that wrapper or register Archify.
